## 1 (code runs 1-2)
Starting the session. Nothing measured yet. I first look at the practice data (how big the reference CIFs are in atoms and tokens, which sources there are) so I can choose a diagnostic problem set. The model is the plain Qwen2.5-7B-Instruct, so I expect the dominant failure to be format (prose / markdown fences around the CIF, making the raw text unparseable) and I will check this in the first generation pass.

## 2 (forward pass 1)
The practice data are 27,380 train and 5,000 val crystals; reference CIFs are P1 pymatgen-style files with 6-52 atoms (median 22) and 555-2,942 tokens. I fix a random permutation of val (numpy RandomState(0)) and call consecutive blocks of 256 ids S0, S1, ... Pass 1 is the diagnostic: the ORIGINAL model generates 2 samples for each of the 256 problems of S0 with the evaluation protocol, saving residual-stream and MLP activations at all layers. I want the outcome counts (not parseable / invalid / wrong composition / no match / match) and to read failing texts. If my guess is right, most answers will be unparseable because of markdown fences or prose around the CIF.

## 3 (code runs 6-9)
Pass 1 failed inside the harness (the activation worker ran out of GPU memory; not counted), but the generation part had finished and left gen_1.jsonl with 512 graded answers of the original model on S0. Result: 488/512 not parseable, 19 valid but wrong composition, 5 valid no match, 0 matches; every answer starts with prose ("To generate a CIF ...", "Certainly! ...") and contains a ``` fence; 77 are cut at the token limit. So the raw-text grading kills nearly everything before the structure is even looked at. Now I build a local grader with pymatgen (same recipe as the evaluation: Structure.from_str, validity, StructureMatcher(stol=0.5, ltol=0.3, angle_tol=10)) and re-grade only the fenced block of each answer. This tells me how much a pure format repair (no prose, no fence, stop after the CIF) could give, and what the next failure category would be (composition? symmetry?).

## 4 (code runs 10-11, forward pass 1)
Re-grading only the fenced block of each original answer still leaves 423/512 unparseable (no loop_, invented tags, one value per loop, wrong column counts), 71 valid with the wrong composition, 17 valid no match and 0 matches. So the failure is not just the prose around the CIF: the model's own free-style CIF is malformed and, when it parses, its symmetry-expanded contents do not give the requested composition. The reference answers are pymatgen CifWriter files (P1, every atom listed) starting with '# generated using pymatgen', a format Qwen has certainly seen many times. Hypothesis: if the answer starts with that header the model's own prior will continue in the well-formed pymatgen format, so the thing to repair is the decision made at the first answer tokens. Pass 1 tests the premise densely: the original model reads prompt + full reference CIF + <|im_end|> for ~300 train problems and I get its log-probabilities and top-20 predictions at every token. I expect: very low probability for the first header tokens ('#', ' generated'), high probability for the fixed lines once the header is in context, and I will look at what is poorly predicted (formula-unit count Z, cell lengths, atom count, end of file).

## 5 (code runs 12-15, forward pass 2)
Pass 1 (teacher-forced on 428 train references) shows that the original model gives the reference format almost no probability at a handful of decision points and is fine elsewhere: first token '#' has mean log-prob -19.0, ' generated' -12.2, ' using' -4.7, ' pym' -11.6, 'data' -6.0, the line starts '_sym' -5.3, '_cell' -5.3, 'loop' -6.0, and the end-of-answer token -6.2 (it predicts another newline), while most other template tokens are near 0 once the format is in context (mean per-token log-prob after line 19 is about -0.2, mostly coordinate digits). So the model can continue the pymatgen format but never chooses it. Before building edits I want to know what the reachable ceiling is: pass 2 is a generation pass with my own user messages on 128 val problems (first half of S1), variant A = the task plus one worked example and an instruction to answer with the raw CIF only, variant B = instruction only, 2 samples each. I grade the answers with my local grader (it agreed with the harness on 120/120 answers). If format-following answers match the reference at a useful rate, pushing the weights toward this behaviour is worth it; I will also see the next failure categories (wrong composition, endless atom lists, ...) in the well-formatted regime.

## 6 (code runs 16-20, forward pass 3)
Pass 2 (ceiling test with my own prompts, graded locally): with a one-shot example every answer starts with '# generated using pymatgen' and follows the template, but there are still 0 matches in 256 answers (193 not parseable, 43 valid wrong composition, 17 valid no match, 3 invalid); with the instruction only, also 0/256. Reading the texts shows the next failures inside the template: (i) the model writes a real space-group symbol and then a long invented list of symmetry operations instead of the single 'x, y, z' (sometimes hundreds, running to the token limit), (ii) all atoms get the same coordinates 0 0 0, copied line after line (pymatgen then finds no structure), (iii) the number of atoms rarely equals the reference (9.5% of parseable answers), (iv) 4% write 'data(' instead of 'data_'. So format alone is not enough, but each of these is a concrete mechanism at an identifiable decision point, and they are exactly the points where pass 1 showed low log-probability of the reference token ('P 1': -5; 'loop_' after the first symmetry operation: -6.0). Plan: install position-keyed corrections in the LAST MLP (model.layers.27.mlp.down_proj), where an edit changes only the logits at the keyed positions and cannot disturb any downstream computation, so the activations measured on the original model stay exact as long as the text so far follows the template. For that I need the last-layer MLP activations (the down_proj inputs, the 'keys') at the decision points and at ordinary positions (to make keys specific). Pass 3 records them, with the residual stream before/after the last block, on 200 train references truncated to 1000 tokens. Expected: keys at decision points are well separated from ordinary positions (to be checked offline before any edit is tested).

## 7 (code runs 21-24)
Pass 3 confirms pass 1 on other problems: 45 rigid template tokens have mean log-prob below -0.3; the harmful ones are '#' (-19; the model wants 'To'/'Certainly'), ' generated' (-12.2), ' pym' (-11.6), 'data' (-6.0), the line starts '_sym' (-5.3), '_cell' (-5.3), '_sym' of Int_Tables (-4.2; it wants 'loop'), '_formula' of formula_units_Z (-3.3), 'sym' of the symmetry loop (-5.6; it wants the atom loop), the '1' of 'P 1' (-6.6; it wants '4', '3'), 'loop' after the first symmetry operation (-5.8; it gives p~1 to writing a second operation, which is the runaway symmetry list seen in pass 2), and ' _' before _atom_site_occupancy (-3.2). I now build the keys for a last-layer edit: the down_proj inputs of model.layers.27.mlp at the position just before each such token (mean over 160 fit texts), and the uncentered second moment C of these activations over all answer positions, so that each key can be whitened (w_c = C^-1 k_c / k_c^T C^-1 k_c, the closed-form rank-one 'ROME' key). I keep 40 texts aside to check offline that w_c responds with about 1 at its own decision point and about 0 everywhere else. No weights are changed yet.

## 8 (code runs 25-26)
Offline check of the keys (40 held-out texts): each whitened key answers 1.00 on average at its own decision point (minimum 0.77-0.99) and at most 0.03-0.25 at any other answer position (rms 0.001-0.009), so the last-layer MLP activations identify the template positions almost perfectly. The logit gaps to close are up to 20 nats ('#'); one nat of margin costs a residual change of norm about 1.5-2.7 (the final residual has rms 4.5 per coordinate, norm about 270), so the needed vectors are 5-20% of the residual norm at the keyed positions and practically zero elsewhere. Edit E1: down_proj += sum_c beta_c d_c w_c^T over 30 decision classes, with d_c = unit vector along gamma*(U_target - mean competitor unembedding) and beta_c = (largest observed gap + 8 nats) * rms / sensitivity. One technical point: the update entries (about 1e-4) are below the bfloat16 spacing of typical weights (1.2e-4 at 0.02), so rounding to nearest would erase most of it; I therefore put the edited tensor on the bfloat16 grid myself with unbiased randomized rounding, which preserves the low-rank update in expectation and adds only noise comparable to the rounding noise already present. I check the predicted margins by logit-lens arithmetic on the recorded held-out final hidden states before spending a pass.

(1) The tool's hidden_L28 is saved after the final norm (a logit lens without the norm reproduces the recorded log-probs to 0.006 nats), so I reconstructed the pre-norm scale of the last residual from h27 + W0*k (rms about 6-9, not 4.5) and resized the edit accordingly. (2) Boosting ' generated' also boosted ' Generated', so each value direction now also subtracts the mean unembedding of the target's 20 nearest neighbours. Prediction: nearly all answers now start with the pymatgen header, use 'P 1' with a single symmetry operation and reach the atom loop; I expect parseability to rise sharply, and I will read what goes wrong next (atom count, repeated coordinates, missing stop).

## 10 (code runs 36-40)
Pass 4 (E1, S0 x 2): the edit does exactly what the offline check predicted at the keyed positions (512/512 answers start with '# generated using pymatgen' + data_<formula>), but 429/512 then leave the template at the end of line 1: the model writes a blank line after data_<formula> (a token at a variable position that I had not keyed), and from there it free-styles; 62 answers follow the whole header. ## 11 (code runs 41-52, forward pass 5)
I rebuilt the edit as E2 after three offline findings. (1) Independent keys leaked into digit positions (e.g. the 'newline after the cell length' key answered 0.1-0.6 at the 5th-7th decimal and would have cut numbers short): I now solve all keys jointly, W = (Kbar C^-1 Kbar^T)^-1 Kbar C^-1, over 178 valued classes and 135 'protected' classes (digit, formula, label positions) whose response is constrained to zero. (2) A value along the raw unembedding row of <|im_end|> boosted unrelated rare tokens more than the target; values are now whitened with the covariance of the unembedding rows, d = Sigma_U^-1 (U_t - U_competitors), which keeps the shift on unrelated tokens at about 1-2% of the target shift. (3) 'The atom list is complete' is linearly readable in the last MLP: a key built from the ends of final atom lines answers about 1.0 at held-out true ends and 0.01 at 90% (0.6 at 1%) of non-final line ends, much more selective than the <|im_end|> logit itself. E2 therefore contains: every rigid header token (lines 0-25, 163 classes), the atom-line format (two leading spaces, label index 0 on the first atom, multiplicity '1', occupancy '1.0'), 'no digits' at the start of the formula sum and after the occupancy, and the stop rule (+11 nats on <|im_end|>, -10 on a blank line, keyed on list-complete). Offline on held-out texts: reference token top-1 at 99.7% of keyed positions, stop chosen at 86% of true ends and 1.3% of non-final line ends, KL 0.0014 elsewhere. Pass 5 tests E2 by generation on 128 random problems (S0[:128]) and 128 small-cell problems (<= 10 atoms), 2 samples each. Prediction: most answers parse; the open questions are atom count, composition and whether any small cell matches.

## 12 (code runs 53-54)
Pass 5 (E2) was a clear negative: 499/512 not parseable, 72% of answers cut at the token limit, 0 matches. Reading the texts shows three separate causes, all traceable to my edit. (1) First line: after '#' the model sampled ' Generated' (capital G, a near-duplicate token that the whitened value direction boosted almost as much as ' generated' and that the model prefers by about 6 nats), then left the header ('# Generated CIF File for ...' and a ``` fence); my offline check had pooled all keyed positions and hid this one class. (2) The template after 'data_' was followed even in that context, and atoms are now written one per line with multiplicity 1, but the list never ends: elements before the last one switch after the right count (e.g. B1-B3 then O1...), the last element runs on (O1...O59) to the token limit. I had forced the two-space atom-line start after every newline and suppressed the blank line, which removed the model's own ways of ending the list, and the list-complete stop key evidently did not fire in these contexts. (3) Banning digits at the start of the formula sum made the model write the sum without counts ('Rb' 'B' 'O'), removing the counts it could have used. I quantify these before rebuilding.

## 16 (code runs 78-81)
Passes 8-9 (E3 on 512 train problems stratified by lattice class, then teacher-forced reading of the model's own headers): the edited model never writes alpha=60 (fcc refs: 103/115 answers 90/90/90, 0 matches; cubic-P refs: 5/115 match). Strength chosen so that the token flips only when the key responds above about 0.5. First I measure the gaps to close.

## 17 (code runs 82-83, forward pass 10)

Independent check: the fcc key, built from the model's own headers of pass-8 problems, answers 0.55 on average (68% above 0.5) for fcc references and above 0.5 for only 0-5% of the other classes on the 880 different problems of pass 7. ## 18 (code runs 84-87, forward pass 11)
Pass 10 (E4) is a negative result and I revert to E3: 4 matches instead of 5 on the same problems, unparseable answers up from 206 to 269, cut answers from 52 to 78. The lattice keys did act as intended at their positions (hexagonal references: gamma=120 in 60/88 answers instead of 18/88; fcc references: 60-degree cells in 11 answers instead of 0, e.g. K3WF6 a=b=c with 60/60/60), but the keys are noisy readouts: on reference texts their off-position response has rms 0.10-0.17 (max 2-4) against 0.002-0.04 for template keys, which with +17 nats per unit shifts the logit of '6' (or '1') by 1.5 nats rms at every position, enough to produce runs of '666...' and more duplicate coordinates (34% -> 42%). I had seen this in the offline check (KL 0.10, top-1 changed at 10% of unkeyed positions) and should not have spent the pass. Conclusion: a lattice-dependent decision cannot be a linear readout of the last-layer MLP activations; it needs a gate, i.e. a neuron that is active only at the angle position AND reads the lattice feature there: activation = silu(g.x)*(u.x) with g a position detector (strongly negative everywhere else, so the product vanishes) and u the lattice direction. That means repurposing a neuron (gate_proj/up_proj rows and down_proj column) in an MLP whose input I can reconstruct exactly; for block 27 (model.layers.26) the input is RMSNorm(hidden27 - W_down26 @ mlp_act27). Pass 11 records hidden 27 and mlp_act 27 on the model's own headers (512 pass-9 texts, lattice labels known) and on 300 reference headers.

## 19 (code runs 88-94, forward pass 13)
The gate works on paper. From hidden 27 and mlp_act 27 I reconstruct the input x of block 27's MLP exactly (recomputed activations agree with the recorded ones to 0.5%). In that space (i) a bias-like direction exists (b.x = 0.98 +- 0.03 at all 258,000 recorded positions, including atom lists of full generated texts), (ii) the positions 'about to write the first digit of alpha / gamma' are linearly separable from every other position (response >= 0.62-0.80 at own positions, <= 0.26 anywhere else), and (iii) the lattice class is as decodable as in the last layer (fcc at alpha: 5-fold CV recall 87% at 3.8% false positives; hexagonal at gamma: 67% at 12%). I repurpose three near-dead neurons of model.layers.26.mlp (largest |activation|*|down column| over 6,000 sampled positions 0.7-0.9 against a median of 6.5): gate row = 60*(position detector - 0.42*bias), up row = lattice direction minus threshold, down column = whitened unembedding direction of the target digit. Neuron A: alpha position x fcc -> '6'; neuron B: gamma position x hexagonal -> '1'; neuron C: gamma position x 'alpha=beta=60 in context' -> '6'. On all recorded positions the activation away from the own position is below 5e-5 (logit shift 0.000), and at the own position the implied shift is +28 nats for fcc and -9 for the other classes (in-sample). What I cannot compute is how block 28 reacts to this write, so pass 13 measures it: teacher-forced pass of the model with ONLY these neurons (E3 dropped) on the 512 own-header texts and the 220 full generated texts, to compare token log-probs with the original ones from passes 9 and 12. Prediction: P('6') at alpha jumps for fcc references only; log-probs at all other positions unchanged to within about 0.01.

## 20 (code runs 95-97, forward pass 14)

## 21 (code runs 98-102)
Passes 14-15 (teacher-forced calibration of the lattice circuit): (a) the position-keyed last-layer bias behaves as designed once its key is whitened with the within-position covariance of the model's own headers (cross-validated response 1.00 +- 0.03 instead of +- 0.47): regression of the measured shift gives 9.3 nats per unit of bias response. (b) The gated block-27 neuron has a narrow linear range: at implied slope 24 the measured effect is +5.3 nats per unit of lattice response (efficiency 0.22), but at implied slope 36 the effect reverses sign (-3.2 per unit; non-fcc headers then got '6' in 95%): the last block does not transmit large writes faithfully. So the neuron must stay at about +-12 implied nats and the bias must do the constant part. (c) Neuron B (hexagonal -> gamma '1') is right in that range and works: P('1') at gamma 0.99 for hexagonal references and 0.005-0.04 for the others (in-sample; CV of the direction: 67% recall, 12% false positives). (d) A flipped alpha propagates to beta by itself (P('6') 0.95 after alpha=60) but not to gamma: in synthetic headers with alpha=beta=60 the model (with the gamma bias) writes '1' in 360/448, i.e. 60/60/120. I therefore add a third gated neuron C at the gamma position reading 'alpha=beta=60 was written' (a context feature, not the noisy lattice readout), which raises '6' and lowers '1' there and does the opposite elsewhere, replacing the unconditional gamma bias.
